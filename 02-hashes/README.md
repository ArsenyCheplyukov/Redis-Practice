# 02 — Hashes

Hash — структура данных Redis для группировки полей под одним ключом.
Аналог: словарь / map / struct.

## Команды

### Чтение / запись

- `HSET key f1 v1 f2 v2 ...` — записать/перезаписать одно или несколько полей
- `HGET key field` — прочитать одно поле
- `HMGET key f1 f2 ...` — прочитать несколько полей за один round-trip
- `HGETALL key` — все поля + значения (плоский array в RESP2)
- `HKEYS key` — только имена полей
- `HVALS key` — только значения
- `HLEN key` — количество полей
- `HEXISTS key field` — есть ли поле (0/1)
- `HSTRLEN key field` — длина значения поля
- `HDEL key f1 f2 ...` — удалить поля (удаляет hash целиком если поле последнее)

### Условные / числовые

- `HSETNX key field value` — записать только если поля НЕТ. Аналога `XX` нет.
- `HINCRBY key field N` — атомарный +N к полю. Нет команды `HINCR` без `BY`.
- `HINCRBYFLOAT key field N`

### Deprecated

- `HMSET` → используй `HSET` (с Redis 4.0)

## Hash vs N отдельных string-ключей

**Когда что выбирать:**

|                                  | Strings (`user:42:name`, `user:42:email`) | Hash (`user:42` с полями)                                          |
| -------------------------------- | ----------------------------------------- | ------------------------------------------------------------------ |
| Поиск                            | O(1), одинаково                           | O(1), одинаково                                                    |
| Память (3 поля × 1M юзеров)      | ~600 MB                                   | ~100 MB (listpack encoding)                                        |
| Один TTL на сущность             | Нет, надо ставить N TTL                   | Да (TTL на key целиком; per-field TTL — отдельный механизм с 7.4+) |
| Один DEL чистит всё              | Нет, DEL с N аргументами                  | Да                                                                 |
| Прочитать весь профиль           | MGET с явным перечислением                | HGETALL                                                            |
| Частичное обновление одного поля | SET одного key                            | HSET одного field                                                  |

**Правило:** если поля логически принадлежат одной сущности и обычно читаются/удаляются вместе — **hash**. Если поля независимы (например, разные сессии или счётчики разных метрик) — strings с TTL.

## Encodings

- `listpack` — компактное представление, до 128 полей и значений ≤ 64 байт каждое (defaults). Главный плюс hash по памяти — именно этот encoding.
- `hashtable` — когда любой из лимитов превышен. Дороже по памяти, но O(1) per-field вместо линейного скана listpack.

Проверка: `OBJECT ENCODING <key>`. Лимиты настраиваются в `redis.conf`:

- `hash-max-listpack-entries 128`
- `hash-max-listpack-value 64`

## Асимметрии API (важно)

### Return values: hash → integer, string → status

| Команда  | Не записал    | Записал       |
| -------- | ------------- | ------------- |
| `SET NX` | `(nil)`       | `OK`          |
| `HSETNX` | `(integer) 0` | `(integer) 1` |

Hash-команды возвращают **число изменённых полей**, не статус.

### Несуществующий ключ

| Команда            | Возврат         |
| ------------------ | --------------- |
| `GET nokey`        | `(nil)`         |
| `HGETALL nokey`    | `(empty array)` |
| `HGET nokey field` | `(nil)`         |
| `HLEN nokey`       | `(integer) 0`   |

### Нет команды `HINCR` без `BY`

Только `HINCRBY key field N`. Для строк есть и `INCR` и `INCRBY`, для hash — только с явным числом.

## Внутреннее устройство ответа `HGETALL`

В RESP2 (старый протокол, дефолт в CLI) возвращается **плоский array**:

```
1) "name"
2) "Bob"
3) "email"
4) "bob@example.com"
```

В RESP3 — нативный map. Клиентские библиотеки парсят в dict, в `redis-cli` видишь сырой формат.

## Типичные ошибки этой сессии

- **Применение string-команд к hash-ключу:** `GET user:50` на hash → `(nil)`. Hash-ключ читается только `H*`-командами. Аналогично `HGET` на string-ключ упадёт с `WRONGTYPE`.
- **Опечатка namespace** (`status:user:42` vs `stats:user:42`) — типичная классика, особенно с длинными ключами. В реальном коде → константы / билдеры ключей, не голые строки.
- **Заблуждение "hash быстрее искать":** поиск ключа в Redis всегда O(1), независимо от структуры. Hash экономит память и группирует операции — не ускоряет lookup.
